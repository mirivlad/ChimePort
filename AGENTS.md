# Руководство для ИИ-агентов и разработчиков

## Источник истины

Перед написанием кода изучить `README.md`, `docs/01-PRODUCT.md`, `docs/02-ARCHITECTURE.md`, `docs/03-API.md`, `docs/04-DELIVERY.md`, `docs/05-SECURITY.md`, `docs/07-ROADMAP.md` и `docs/08-DECISIONS.md`.

Сервер и веб-панель выпущены как v0.1.2; Android остаётся alpha и публикуется отдельным APK. **Не выдавать PWA/Web Push, `/devices`, OpenAPI и другие запланированные функции за работающие.** Реализованные маршруты проверять по `server/internal/app/app.go`, структуру SQLite — по `server/internal/app/store.go`, а не по ранним проектным требованиям.

## Нельзя нарушать

1. Проект полностью self-hosted; не вводить обязательный центральный сервис, регистрацию в облаке или Google API.
2. Android должен иметь возможность подключать несколько **независимых** серверов по URL; не хардкодить публичный домен автора.
3. Публичной регистрации нет; пользователей создаёт администратор.
4. Разделить `source token` (только публикация) и пользовательские сессии (чтение/настройки).
5. Успешный HTTP ответ на публикацию — только после commit в БД.
6. Синхронизация после офлайна обязана работать независимо от мгновенного транспорта.
7. Отсутствие дубликатов при повторной публикации и синхронизации — проверяемый контракт.
8. Android-системные Notification Channels и системный DND имеют приоритет над фантазиями интерфейса; не обещать программно переопределять выбор пользователя.
9. Любой секрет в логе, токен в URL или отсутствие серверной проверки доступа — блокер релиза.
10. Избегать избыточных сервисов: монолит + SQLite для MVP, если не доказано обратное.

## Порядок работы

- Каждая задача: назначить раздел roadmap/ADR, описать план и критерии приёмки.
- Сначала написать тест на инвариант, затем реализация и документация изменений.
- Изменения API: обновить OpenAPI (когда появится), примеры и тесты совместимости.
- Изменения SQLite: версионированная миграция, тест миграции/rollback-политики, проверка восстановления backup.
- Изменения Android доставок: тест offline/reconnect/два сервера, исключение дублей, работа quiet hours.
- Новые зависимости: обосновать размер, лицензии, угрозы и необходимость.
- Перед публичным релизом проверять LICENSE (AGPL-3.0-only), сборки и инструкцию установки. Android release APK требует закреплённой подписывающей идентичности.
- В конце каждой задачи кратко зафиксировать изменённые файлы, тесты, известные ограничения и обновлённые документы.

## Обязательная проверка документации перед релизом

1. Сверить список API/форматы с реальными обработчиками `server/internal/app/app.go` и тестами; планируемые endpoints помещать только в раздел «не реализовано».
2. Обновить README: поддерживаемые возможности, точную версию сервера, совместимый опубликованный Android APK, Quickstart, ссылки и известные ограничения.
3. При смене Docker-версии синхронизировать `deploy/compose.portainer.yaml`, `.env.example`, инструкции Portainer, backup/restore, релиз-ноты и workflow; не перепубликовывать уже существующий immutable tag.
4. Для изменения SQLite обновить документы схемы, проверить миграцию и восстановление с резервной копии; указывать фактический номер schema.
5. При Android-релизе указать `versionCode`/`versionName`, подтвердить continuity подписи и проверить обновление поверх ранее опубликованного APK.
6. Проверить все относительные ссылки Markdown, опечатки и невозможность случайно опубликовать секреты; отдельно отметить PWA/Web Push как план до реальной реализации.
7. Не смешивать исторические требования/ADR, roadmap и руководство к *доступной* версии. Документировать поддерживаемые команды, не выдавая запланированное за работающий сценарий.

### PWA/Web Push M3

Перед выпуском проверять Service Worker на отсутствие кэширования API/токенов, разрешение только по user gesture, отсутствие SSRF через push endpoint, авторизацию и отзыв подписок вместе с сессиями, постоянство VAPID после restore. Не сливать и не деплоить миграцию schema 4 без бэкапа и проверки отката. [Проверки](docs/16-PWA-WEBPUSH.md).

# 01. Продукт и требования

**Статус:** draft v0.1, 2026-11-03. **Название:** ChimePort (рабочее).

## 1. Миссия

Создать простой, полностью контролируемый владельцем self-hosted сервис, который принимает события от программ через HTTP API и показывает их человеку в браузере или на Android. Заменить Telegram-ботов и разрозненные уведомлялки там, где пользователю нужен именно личный журнал оповещений, а не чат.

Продукт самостоятельный: любой пользователь поднимает свою инсталляцию на собственном домене и скачивает один и тот же универсальный Android-клиент.

## 2. Целевые сценарии

1. **Дом:** Home Assistant сообщает об открытии двери, протечке, температуре, состоянии датчиков.
2. **Администрирование:** мониторинг присылает о падении сервиса, успешных/неуспешных бэкапах, обновлениях.
3. **Личные скрипты:** cron и автоматизация вызывают API одной командой.
4. **Несколько независимых инсталляций:** телефон подписан на домашний и рабочий серверы, но сам сервис не объединяет их на своей стороне.
5. **Семья/команда:** администратор создаёт отдельных пользователей и даёт им доступ к нужным потокам.

## 3. Роли и сущности

- **Администратор сервера:** первоначальная настройка, создание/блокирование пользователей, системные лимиты и диагностика.
- **Пользователь:** обычный вход по логину/паролю, управление своими токенами, каналами/подписками, устройствами и настройками.
- **Источник (source):** логическое приложение, например `home-assistant`; имеет имя, описание и один/несколько **токенов публикации**.
- **Канал:** поток событий с постоянным идентификатором и читаемым именем, например `home/security`.
- **Подписка:** разрешение пользователя получать события канала; является отдельной сущностью от прав источника публиковать в канал.
- **Устройство:** конкретный веб-сеанс/PWA или подключение Android, со своей настройкой доставки и состоянием синхронизации.
- **Сообщение:** принятый и сохранённый факт события, не обязательно немедленно показанный пользователю.

**Требование изоляции:** права и каналы разных пользователей не должны пересекаться случайно. Для MVP: личные каналы владельца; совместное использование каналов несколькими аккаунтами — отдельный этап с явным ACL.

## 4. Обязательные функции MVP

### Сервер

- Развёртывание одним контейнером и persistent volume через Docker Compose/Portainer; HTTPS предоставляется reverse proxy.
- Без публичной регистрации; первый администратор через безопасный bootstrap, последующие пользователи — из админки.
- Логин/пароль для людей, безопасные сессии; токены для источников с названием, описанием, областью доступа, сроком действия и отзывом.
- CRUD личных каналов, подписок, именованных источников и токенов.
- HTTP API v1 с JSON, Bearer auth, документацией и кодами ошибок.
- Приём сообщения в конкретный канал; запись в SQLite **до** успешного ответа API.
- История, пагинация, состояние прочтения, политика хранения.
- Синхронизация после обрыва, идемпотентность повторной отправки.
- Онлайн-транспорт для клиентов (WebSocket или SSE с явной досинхронизацией).

### Веб-интерфейс и PWA

- Адаптивная веб-панель, вход, общая лента, отдельные каналы, поиск/фильтрация (в MVP допустима базовая фильтрация).
- Страницы управления токенами, источниками, каналами, подписками и устройствами.
- Настройка уведомлений и подписка на Web Push по разрешению пользователя, если поддерживается браузером.
- Понятная индикация «уведомления недоступны/запрещены/ожидают разрешения».

### Android

- Самостоятельный Android-клиент, устанавливаемый APK, без обязательного Google Play.
- Настройка адреса сервера и входа; возможность подключить **несколько** серверов одновременно.
- Единая входящая лента, фильтры по серверу и каналу; отдельная лента для каждого канала.
- Уведомления в фоне по доступному транспорту, восстановление истории без дублей.
- Глобальные настройки и переопределения на уровне сервера/канала: звук, вибрация, тихие часы и дни недели.
- Диагностика соединения и ограничений фоновой активности, без обещаний гарантированного push.

## 5. Критерии успеха

- Отправка `curl` с действующим ограниченным токеном создаёт запись и возвращает ID.
- После выключения телефона, поступления нескольких сообщений и переподключения история совпадает с сервером без дублирования записей.
- Два независимых сервера видны в одном Android-клиенте, их URL и учётные данные изолированы.
- Пользовательские токены нельзя использовать для админских операций или чтения чужой истории.
- Канал «загрузки» можно сделать беззвучным, а «безопасность» — звучащим в разрешённые часы.
- После рестарта контейнера сообщения, пользователи и настройки сохранены.

## 6. Не делаем в первой версии

- Публичную регистрацию, федерацию/общий каталог серверов.
- Чат между людьми, двухстороннюю переписку, редактирование чужих сообщений.
- Обязательный облачный сервис, монетизацию и телеметрию по умолчанию.
- SMS/звонки, гарантированную доставку в обход ограничений Android.
- Обязательную FCM-интеграцию, iOS-приложение, загрузку произвольных медиа и файлообмен.
- Сложный маршрутизатор правил, кластеризацию и высокодоступный отказоустойчивый режим.

## 7. Нефункциональные требования

- Приоритет: понятность, прозрачность работы, простое резервное копирование.
- Интерфейс: русский и английский через локализуемые строки; минимум зависимостей от SaaS.
- Секреты не пишутся в логи; пароли и API-токены не хранятся открытым текстом.
- Публичный HTTPS — обязательное условие для production и Web Push.
- Не обещать показатели надёжности без измерений на реальных устройствах.
- Сервер должен корректно обслуживать небольшую домашнюю инсталляцию без Redis и отдельного брокера.

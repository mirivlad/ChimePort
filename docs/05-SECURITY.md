# 05. Модель безопасности

## 1. Основные угрозы

- Утечка `source token` из скрипта/лога/репозитория.
- Перебор пароля и подбор сессий.
- Чтение чужих каналов при неправильной проверке `user_id`.
- Массовый спам/заполнение диска через валидный токен.
- CSRF/XSS в веб-панели; WebSocket с неверной авторизацией.
- Утечка содержимого сообщений через push payload, логи и резервные копии.
- Подмена сервера по тому же URL после смены DNS/развёртывания.
- Неправильные права администратора и опасный bootstrap.

## 2. Обязательные меры

- Production — только HTTPS с валидной цепочкой. Cookies: `Secure`, `HttpOnly`, `SameSite`; для операций с Cookie-сессией — CSRF защита.
- Пароли — Argon2id с актуальными безопасными параметрами, солью и контролем скорости входа; никакой возможности восстановить исходный пароль.
- Source token — криптографически случайный, достаточной энтропии, хранение только криптографического хэша/HMAC с серверным ключом и префикса для поиска; полное значение показывается один раз.
- Токену задаётся минимальный scope (`messages:write`) и список конкретных каналов. По умолчанию — **не** все каналы.
- Дата истечения, отключение токена, аудит факта использования и ротация.
- Пользовательские сессии и API-токены имеют раздельную модель полномочий; токен отправки не читает историю.
- Все SQL-запросы параметризованы. Владение каналом, сообщением и источником проверяется в backend.
- Ограничения размера тела и количества запросов; политика квот/retention, защита от истощения диска.
- Заголовки защиты веба (CSP, HSTS при корректной настройке), защита от XSS и запрет HTML в содержимом сообщений по умолчанию.
- Не выводить URL с bearer token, пароли, HTTP Authorization и полные Web Push ключи в логи.
- Отдельный ограниченный ключ для фонов Web Push/VAPID и его сохранение в бэкапе с контролем доступа.
- Для push payload передавать **минимум**: ID или нейтральное название события; приватные заголовки/тела — по решению пользователя и возможностям клиента, с ясным описанием зависимости от push-провайдера.
- Refresh credentials клиента и токены в Android защищаются средствами Android Keystore; logout удаляет локальные токены и приватный кэш по выбору пользователя.

## 3. Bootstrap

Первое создание администратора должно требовать явной команды/разовой процедуры в контейнере или через одноразовый setup token с коротким TTL и защитой от удалённого захвата. Запрещены пароли по умолчанию, которые остаются действующими. После начальной настройки bootstrap блокируется.

## 4. Изоляция и аудит

- По умолчанию каналы личные. Совместный доступ — отдельная фича с явными приглашениями/ACL, только после тестов изоляции.
- Пользователь не должен видеть факт существования чужого приватного канала через `404`/`403` различия, если это позволяет перечисление.
- Аудит: входы/попытки входа, создание и отзыв токенов, выдача роли, создание пользователей, изменение политики retention. Без тел сообщений и секретов.
- Админ-интерфейс не является невидимой дверью к приватным уведомлениям пользователей. Доступ администратора к содержимому — отдельное решение с раскрытой политикой, не по умолчанию.

## 5. Инсталляция и резервное копирование

- Контейнер по возможности не root, readonly filesystem где возможно, отдельный каталог данных с минимальными правами.
- SQLite, ключи/VAPID, instance_id и конфиг должны восстанавливаться согласованным backup-процессом.
- Не копировать работающую SQLite-БД обычным `cp` при активных записях: использовать online backup API/`VACUUM INTO`/остановку контейнера с согласованной копией.
- Удаление данных/срок хранения должны быть понятны администратору.

## 6. Пределы гарантий

Это не E2EE-мессенджер: сервер обрабатывает открытый текст сообщений, а его администратор технически контролирует хранилище. Для строгого E2EE нужна отдельная модель ключей. Уведомления не предназначены как единственный канал пожарной/медицинской/аварийной безопасности.

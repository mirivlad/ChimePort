# 04. Доставка, Android и PWA/Web Push

**Состояние v0.1.3:** сервер хранит сообщения и раздаёт REST-историю и SSE; Android alpha поддерживает несколько серверов, системные уведомления, настройки звука и тихие часы (с ограничениями ОС). **PWA, Web Push/VAPID и серверные Web Push subscriptions реализованы с v0.1.3.** Ручное тестирование браузеров необходимо перед использованием как основного канала.

## 1. Четыре независимых факта

1. **Accepted/stored:** сервер провалидировал сообщение и зафиксировал транзакцию в БД.
2. **Transport attempted:** сервер попытался отправить сигнал активному клиенту/Web Push endpoint.
3. **Received by client:** приложение подтвердило сохранение сообщения в локальном кэше.
4. **Read by user:** пользователь открыл или отметил запись прочитанной.

Нельзя называть событие `Web Push accepted by gateway` или `WebSocket frame sent` «показано на телефоне». ОС и пользовательские настройки могут предотвратить показ. Доставка минимум один раз на уровне sync допустима; **повторное отображение подавляется по ID**.

## 2. Политика отключённого клиента

- После соединения клиент выполняет досинхронизацию пропущенных сообщений.
- Синхронизированное старое сообщение появляется в истории, но **по умолчанию не вызывает шквал звуковых системных уведомлений**.
- Для сообщений последних N минут можно включить оповещение; N — опциональный локальный параметр.
- При больших пропусках можно показать одно агрегированное «Получено 24 новых сообщения», если это разрешено.
- Удалённые по retention события не восстанавливаются; разрыв показывается явно.

## 3. Android: мультисерверный клиент

- Добавление: URL сервера -> проверка HTTPS и server `instance_id` -> логин/пароль -> создание клиентской сессии -> регистрация устройства.
- Не хранить один пароль для всех серверов; токены, refresh credentials, кэши и ID находятся в отдельных пространствах.
- Главная лента объединяет записи, сортирует по серверному timestamp (помечая сервер), а при равных временах применяет стабильный порядок. Не путать события разных инсталляций.
- Персональные настройки: **глобально -> сервер -> канал**. Ближайшее явное переопределение имеет приоритет. При отсутствии переопределения используется унаследованная настройка.
- Фон: прямое WebSocket-соединение/периодическая sync при разрешённом ОС режиме; optional foreground service с постоянным уведомлением, если пользователь включил постоянное подключение. Сброс батарейных оптимизаций не требовать молча.
- Система показывает «Последняя успешная синхронизация» и отдельно «Фоновые уведомления могут задерживаться».
- Каждая инсталляция может иметь свои сертификаты, но HTTP без TLS для удалённого подключения не предлагается; LAN-only режим — отдельное сознательное решение.

## 4. Android Notification Channels (системные)

**Важная техническая особенность:** после создания Android `NotificationChannel` приложение не может программно поменять его звук/важность: это делает пользователь в настройках ОС. Поэтому:

- Создавать системные каналы с детерминированными ID на основе локального ID сервера + channel ID (не названия).
- Предлагать встроенную кнопку «Открыть системные настройки звука канала».
- Для пользовательского выбора новой мелодии внутри приложения заранее продумать поддержку управляемой миграции/версии канала, не перезаписывая системные предпочтения без согласия пользователя.
- Не создавать новый системный канал при каждом сообщении.
- Ограничить/группировать количество системных каналов, если у пользователя их сотни; продумать явную политику лимита.
- Вибрация и важность подчиняются системным правам и DND.

Ссылка: https://developer.android.com/develop/ui/compose/notifications/channels

## 5. Расписание тишины

Настройки на уровне global/server/channel:

```json
{
  "enabled": true,
  "timezone": "Europe/Istanbul",
  "quiet": {
    "start": "23:00",
    "end": "08:00",
    "days": ["mon", "tue", "wed", "thu", "fri", "sat", "sun"]
  },
  "sound": "system-default",
  "vibration": true,
  "show_in_tray": true,
  "urgent_override": false
}
```

**Трактовка:** `days` обозначает **дни начала интервала** (например, `fri`, 23:00–08:00 означает с пятницы 23:00 до субботы 08:00). Вечерние интервалы, пересекающие полночь, DST, смену часового пояса и ручную смену даты должны покрываться тестами. Если нужна «всю субботу тихо», лучше отдельный `full_day_mute`, а не неявная интерпретация.

- Во время тишины сообщения **сохраняются и отображаются в ленте**; отключается звуковое/вибрационное/всплывающее оповещение согласно локальным настройкам.
- `urgent_override` пользователь включает сам на нужном канале; это отменяет только правила **самого приложения**, а не режим Android «Не беспокоить» или отключённые системные уведомления.
- Если приложение спало, при восстановлении соединения правило оценивается для момента возможного **показа**, а не для исторического времени отправки.
- Не пытаться обходить системные ограничения «важных» уведомлений без разрешения пользователя.

## 6. PWA и Web Push (реализовано в v0.1.3)

- HTTPS + Service Worker + Push API + разрешение Notifications API.
- Web Push зависит от push-службы выбранного браузера; приложение не обязано быть открыто на экране, но фоновая доставка не гарантируется.
- PWA **не** умеет гарантированно запускаться как постоянная служба после загрузки Android и не может надёжно задавать произвольный звук каждому каналу.
- Если Web Push запрещён или недоступен, история и получение онлайн через веб продолжают работать.
- У каждой инсталляции свой origin и собственная PWA подписка; общая межсерверная лента — функциональность Android-клиента, не одной PWA разных origin.

Ссылка: https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation

## 7. Возможные транспорты в будущем

- **Реализовано:** серверный SSE + HTTP sync и Android-клиент; PWA Web Push.
- **Потом:** поддержка UnifiedPush через установленный на Android дистрибьютор при наличии совместимой транспортной архитектуры.
- **Опционально:** FCM, но только при ясно описанной модели доступа каждого self-hosted сервера к инфраструктуре отправки. Общий APK и независимые серверы не означают, что произвольный сервер может автоматически использовать один и тот же Firebase-проект без выдачи доверенных учётных данных/шлюза.

Ключевое правило: любой транспорт заменяем; серверная история и API остаются единственным источником истины.
